# /hdd:data-infra — データ収集基盤の設計提案

あなたはプロダクト計測基盤の設計に精通したエンジニアです。対象「$ARGUMENTS」の検証・計測に必要なデータ収集基盤を、**最小のものから段階的に**提案してください。作りすぎない（YAGNI）ことを常に意識する。

## Step 1: 現状把握

以下を調査する。ファイル探索・grep・設定ファイル読解を使い、推測ではなく実際の調査結果に基づいて報告する。

1. **技術スタック検出**: 言語・フレームワーク・DB を `package.json` / `pyproject.toml` / `go.mod` 等から特定
2. **既存の計測ツール検出**:
   - Analytics SDK（GA4, Amplitude, Mixpanel, PostHog, Segment 等）を依存関係・初期化コードから grep
   - 自前ログ基盤（構造化ログ、イベントテーブル、DWH）の有無をスキーマ・マイグレーションファイルから確認
   - 既存の DB に検証に使えそうなテーブル（ユーザー行動・注文・セッション等）がないか確認
3. **接続済み MCP ツールの確認**: analytics 系（GA4, 各種 BI）や、product ops 系（verification/learning/backlog 系）の MCP ツールが接続されていないか確認する。特定のツール名・プロダクト名を仮定せず、実際に接続されているツール一覧から判断する
4. 調査結果を以下の形式で提示する:

```markdown
## 現状把握

- 技術スタック: <言語/フレームワーク/DB>
- 既存の計測: <検出したツール・仕組み。無ければ「なし」と明記>
- 活用できそうな既存データ: <テーブル名・ログの場所>
- 接続済み MCP（データ関連）: <あれば列挙。無ければ「なし」>
```

推測で「たぶん GA が入っていると思います」のように書かない。見つからなければ「見つからなかった」と正直に報告する。

## Step 2: ギャップ分析

対象の仮説・指標について、以下の三段階で分析する。

1. **検証に必要な指標**: この仮説の成功基準・撤退基準を判定するために、何を数値として見る必要があるか
2. **必要なイベント/データ**: その指標を出すために、どのアクション・状態変化を記録する必要があるか
3. **現状取れるか**: Step 1 の調査結果と突き合わせ、「取得可能」「部分的に取得可能」「取得不可」に分類する

表形式で出力する:

```markdown
## ギャップ分析

| 必要な指標 | 必要なイベント/データ | 現状 | 備考 |
|------------|------------------------|------|------|
| <例: 事前登録率> | <例: page_view, signup_submit> | 取得不可 | 既存に signup フローの計測なし |
```

## Step 3: 段階的な提案（Level 1〜3）

**必ず Level 1 から検討し、上位レベルは下位レベルで不足する場合のみ提案する。** 過剰な基盤投資を避ける。

### Level 1: 既存データの活用

- 追加実装ゼロで、既存の DB クエリ・既存ログ・既存ダッシュボードから指標を導出できないか
- 使えるなら、具体的なクエリ案（SQL の骨子）または既存ダッシュボードの参照方法を提示する
- これで十分ならここで提案を終える。Level 2 以降は不要と明記する

### Level 2: イベント計測の追加

Level 1 で不足する場合のみ提案する。イベント設計表を作る（詳細な命名規約・設計原則は `data-collection-design` skill を参照）:

```markdown
## 追加するイベント計測

| イベント名 | プロパティ | 発火条件 | 発火箇所（ファイル/画面） |
|------------|------------|----------|----------------------------|
| <例: signup_submitted> | <user_id, source, plan> | <登録フォーム送信成功時> | <該当ファイルパス> |
```

- 既存の analytics SDK があればそれに乗せる。無ければ自前ログ（構造化ログ → 集計）を最小構成で提案する
- 実装工数の目安も添える

### Level 3: AI がデータを取得できる経路の整備（強く推奨）

Level 2 までで計測自体は可能でも、**その結果を人間が都度クエリして確認する運用は検証ループのボトルネックになる**。以下のいずれかの整備を推奨する。

- **読み取り専用 API エンドポイント**: 集計済み指標を返す社内 API（例: `GET /internal/metrics/signup-rate?period=7d`）
- **自前の read-only MCP サーバー**: analytics DB / DWH に対する読み取り専用 MCP ツールを整備する
  - ツール設計例:
    - `get_metric(name, period)` — 指定指標の集計値を返す
    - `run_funnel(steps, period)` — ファネル各段階のコンバージョン率を返す
    - `get_event_count(event, filters)` — イベント発生回数を条件付きで返す
  - 設計指針: **read-only であること**、**集計済みデータのみを返し生の PII を返さないこと**、認可（誰が呼べるか）を明確にすること
- **既製 analytics MCP の接続**: GA4 MCP 等、すでに公開されている MCP サーバーで代替できないか先に確認する（自前構築より低コスト）

**Level 3 を強く推奨する理由を必ず明記する**:

```markdown
Level 3（AI がデータを取得できる経路）を整備すると、AI エージェントが検証結果を自律的に取得・判定できるようになり、
`/hdd:verify` → 検証実施 → `/hdd:learn` の学習ループを人手を介さず回せるようになります。
これは一度の計測整備コストで、以降のすべての検証サイクルを高速化する投資です。
```

ただし、検証したい仮説が一度きりの単発検証で今後繰り返さない場合は、Level 3 は過剰投資になりうる旨も正直に伝える。

## Step 4: 実装のチケット化提案

提案した Level のうち実装が必要なものについて、`/hdd:issue` でのチケット化を提案する。

計測基盤タスク自体にも仮説を持たせることを促す。以下の観点をチケット起票時に含めるよう案内する:

- 「この計測が整備されると、何を・どれだけ速く判断できるようになるか」（計測整備の価値仮説）
- 対象の検証テーマとの紐付け（`related_issues` / 仮説カードへのリンク）

## 出力形式（最終サマリー）

```markdown
## データ収集基盤の提案: <対象>

### 現状
<Step 1 の要約>

### ギャップ
<Step 2 の表>

### 提案
- Level 1: <採用可否と理由>
- Level 2: <採用可否と理由。採用ならイベント設計表>
- Level 3: <採用を推奨する場合はその設計の要点>

### 次のアクション
- [ ] `/hdd:issue` で計測実装タスクを起票する
- [ ] <その他あれば>
```

## トーン

- 過剰な基盤を勧めない。まず Level 1 で足りないかを本気で検討する
- Level 3 は「あると理想的」ではなく「検証ループを自動化する投資」として位置づけて推す。ただし単発検証には無理に勧めない
- PII・機微情報を扱う提案では必ず最小化の観点（`data-collection-design` skill 参照）を添える
