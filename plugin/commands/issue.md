# /hdd:issue — 仮説付きチケット作成

「$ARGUMENTS」を元に仮説カードのドラフトを作成し、6 項目のチェックリストで検証したうえで、検出したトラッカーにチケットとして登録します。$ARGUMENTS が空の場合は直近の会話文脈からチケット化したい内容を特定し、ユーザーに確認してから開始します。

## Step 1: 仮説ドラフトの生成

$ARGUMENTS（および会話文脈）から、`${CLAUDE_PLUGIN_ROOT}/templates/hypothesis.md` の形式で仮説カードのドラフトを埋める。埋められる項目は埋め、不明な項目は空欄にせず「不明」と明記したうえで、以下の質問ルールに従う。

- 不明項目はユーザーに質問する。**最大 2 往復まで**。3 往復目に入りそうな場合は、その時点の情報で仮説カードを確定し、残る不明点は仮説カード内に「未検証」「要確認」として明記する
- 選択肢が絞れる質問は AskUserQuestion ツールを使う。自由記述が必要な質問（課題の具体的な内容など）は通常のテキストで問う
- 意見と事実を混同させない（「たぶんユーザーは喜ぶ」は根拠にならない、と指摘する）

## Step 2: チェックリスト検証

生成した仮説カードを、以下のチェックリストで自己採点する。

- [ ] 誰のどんな課題か明文化されている
- [ ] 課題の根拠（観測された事実）が書かれている
- [ ] 成功指標と目標値がある
- [ ] 検証方法と成功基準・撤退基準がある
- [ ] 計測手段が存在する（なければ計測整備タスクを先行させる）
- [ ] 「このタスクをやらない場合に失うもの」が書かれている

全項目を満たせた場合は Step 3 に進む。

### 満たせない場合

作成を拒否せず、AskUserQuestion ツールで以下のいずれかを選ばせる。

1. **「仮説なしチケット」として作成する** — チケット本文の冒頭に `> ⚠️ 仮説なしチケット（HDD checklist 未充足）` を明記し、欠落しているチェック項目も併記して作成する
2. **`/hdd:grill` を先に実行する** — このコマンドを中断し、`/hdd:grill "$ARGUMENTS"` の実行をユーザーに促す
3. **今埋められる範囲だけ埋めて再挑戦する** — Step 1 に 1 往復だけ戻る。それでも埋まらなければ選択肢 1 に倒す

なお、バグ修正・明確な技術タスク（CI 修正等）はこのチェックリストの対象外として扱ってよい。その場合は「バグ修正のため仮説チェックリスト対象外」と明記して Step 3 に進む（Step 2.5 もスキップ可）。計測手段が無い項目については、チケット作成を止めずに「計測整備タスク（/hdd:data-infra）」を別チケットとして先行作成することを提案する。

## Step 2.5: 価値スコアリング（このタスクは本当に今やる価値があるか）

チェックリストとは別に、タスクの相対価値を数値化する。AskUserQuestion ツールで以下 4 軸を 1〜5 で聞く（会話文脈から自明なら聞かずに提案値を示し、確認だけ取る）。

| 軸 | 意味 |
|----|------|
| Impact | 成功したときの事業・ユーザーへの影響の大きさ |
| Confidence | 仮説の確からしさ（根拠となる観測事実の強さ） |
| Risk | 放置・失敗したときの損失の大きさ（機会損失を含む） |
| Effort | 実装・検証にかかるコスト |

優先度スコア = `Impact × Confidence × Risk ÷ Effort`（小数第 2 位まで）。

- スコアと内訳をチケット本文に含める
- スコアが著しく低い場合（目安: 5 未満、特に Confidence 1〜2 かつ Effort 4〜5）は、「このチケットより先にやるべき安い検証があるはず」と指摘し、/hdd:grill での仮説の練り直し、またはより小さい検証タスクへの分割を提案する。それでも作成する判断は尊重する

## Step 3: トラッカーへの登録

`docs/hypotheses/README.md` の「設定」セクションを確認してトラッカー種別を把握する（無ければ `/hdd:init` 相当の検出を簡易実施する）。`${CLAUDE_PLUGIN_ROOT}/templates/issue-template.md` の形式で本文を組み立てて登録する。

1. **GitHub Issues（gh CLI）**: `gh issue create --title "<タイトル>" --body "<本文>"`（必要ならラベル・マイルストーンも指定）
2. **MCP ツール**: 検出済みの issue/backlog/ticket 系 MCP ツールを使って作成する
3. **markdown フォールバック**: `docs/hypotheses/` 内にチケット代わりの `.md` ファイルを作成する（仮説カードと統合してよい）

登録後、発行された issue の URL / ID を記録する。

## Step 4: 仮説カードの保存と相互リンク

1. `docs/hypotheses/` の既存カードの最大連番を確認し、`NNN-slug.md` として仮説カードを保存する
2. カードの frontmatter `related_issues` に Step 3 で発行した issue の URL/ID を追記する
3. チケット本文側にも仮説カードへの相対パスリンクを追記する（Step 3 の登録前に本文へ埋め込むか、登録後に追記編集する）

## 完了報告フォーマット

```markdown
## チケット作成完了

- チケット: <URL または ID>（<トラッカー種別>）
- 仮説カード: docs/hypotheses/<NNN-slug.md>
- チェックリスト: <6/6 充足 | 仮説なしチケットとして作成（欠落: ...） | 対象外（バグ修正）>

### 次のステップ
- 検証方法を詰めるなら `/hdd:verify`
- 計測整備が必要なら `/hdd:data-infra`
```
