# Data Collection Design — 計測・データ収集の設計知識ベース

`/hdd:data-infra` と `hypothesis-first` skill から参照される、計測設計の知識ベース。**測ることが目的ではなく、検証の判定材料を用意することが目的** という原則で設計する。

## イベント設計原則

1. **指標から逆算する**: 「何のイベントを取れるか」ではなく「どの指標・成功基準を判定したいか」から必要なイベントを導出する
2. **行動の意味単位で切る**: UI 操作の 1 クリックではなく、ユーザーの意図が完結する単位（例: `search_executed` であって `button_clicked` ではない）でイベントを設計する
3. **冗長に取りすぎない**: 「後で使うかもしれない」で無限にイベントを増やさない。今検証したい仮説に必要なものから着手する
4. **一貫性を保つ**: 既存のイベント体系がある場合はその命名・粒度に合わせる。新規に体系を作る場合はこのドキュメントの規約を使う

## 命名規約

- **形式**: `<対象>_<動作>`（過去形・スネークケース）。例: `signup_submitted`, `trial_started`, `checkout_completed`
- **動詞は完了形で統一する**: `_clicked` `_submitted` `_completed` `_failed` のように、何が確定的に起きたかを表す
- **画面名・機能名をプレフィックスにしすぎない**: `onboarding_step1_button_clicked` のような画面依存の名前は、画面構成が変わるたびに崩れる。意図ベースの名前（`onboarding_started` 等）にする
- **プロパティ名は一貫させる**: `user_id` / `userId` を混在させない。既存の体系がある場合はそれに従う
- **バージョニング**: イベントの意味を破壊的に変更する場合は新しいイベント名にする（同名で意味を変えない）

### イベント設計表のテンプレート

`/hdd:data-infra` の Level 2 提案で使う形式:

| イベント名 | プロパティ | 発火条件 | 発火箇所 |
|------------|------------|----------|----------|
| `signup_submitted` | `user_id`, `source`, `plan` | 登録フォーム送信成功時 | `src/features/signup/SignupForm.tsx` |

## ファネル設計

1. **ステップは実際のユーザー行動の順序で定義する**（理想の導線ではなく実際の導線）
2. 各ステップに対応するイベントを 1 つずつ紐付ける。複数イベントを 1 ステップに束ねると、どこで離脱したかが見えなくなる
3. ファネル全体のコンバージョン率だけでなく、**ステップ間の遷移率** を見る。どこがボトルネックかが検証・改善の材料になる
4. 検証の成功基準がファネルの特定ステップに関わる場合、そのステップの計測を最優先で整備する

## North Star / 先行指標ツリー

- **North Star Metric**: プロダクトが提供する価値を最も端的に表す 1 つの指標（例: 「週次アクティブな課題解決回数」）。遅行指標であることが多い
- **先行指標（Leading Indicators）**: North Star を動かす前段の、より早く観測できる指標。North Star をツリー状に分解して特定する
  - 例: North Star = 「継続利用率」→ 先行指標 = 「初回価値到達までの時間」「初回セッションでの主要機能利用率」
- 検証の成功基準は、可能な限り **先行指標** から選ぶ。遅行指標は判定までの時間がかかり、検証サイクルを遅くする
- ツリーの分解が曖昧な場合、「この指標が動いたら本当に North Star が動くのか」の因果的な仮説自体を明文化し、それも検証対象にする

## PII 最小化

1. **収集前に必要性を問う**: そのプロパティは今の検証・意思決定に本当に必要か。「あると便利」は収集理由にしない
2. **識別子は最小権限で**: 個人を直接特定できる値（氏名・メール本文・電話番号等）はイベントプロパティに極力含めない。内部 ID で紐付け、必要な時だけ別テーブルで参照する設計にする
3. **集計後は破棄可能にする**: 生イベントログの保持期間を決め、集計済みデータのみを長期保持する
4. **AI エージェントに渡すデータは特に厳格に**: 後述の AI アクセス経路は、集計済みデータのみを返し、生の PII を含む行データを返さない設計を徹底する
5. 法域・社内ポリシーで個人データの取り扱いに規定がある場合はそれを優先する。このドキュメントは一般原則であり、法的助言ではない

## AI アクセス経路の設計パターン

検証結果を AI エージェント（Claude Code 等）が自律的に取得・判定できるようにするための設計パターン。`/hdd:data-infra` の Level 3 に対応する。

### パターン 1: 読み取り専用 API エンドポイント

- 既存の社内 API 基盤に、集計済み指標を返すエンドポイントを追加する
- 例: `GET /internal/metrics/funnel?name=signup&period=7d`
- 認可（誰が・どのトークンで呼べるか）を明確にする。書き込み系のエンドポイントとは権限を分離する
- 既存の API 認証基盤に乗せられるなら、新規 MCP サーバーより低コストなことが多い

### パターン 2: 自前の read-only MCP サーバー

- analytics DB / DWH に対して、**読み取り専用**の MCP サーバーを構築する
- 設計指針:
  - **read-only であること**: 書き込み・更新系の操作は一切公開しない
  - **集計済みデータを返す**: 生の行データではなく、集計・匿名化済みの値を返す
  - **ツール粒度は用途ベース**: 汎用 SQL 実行ツールではなく、目的別のツールを用意する（任意 SQL を許可すると PII 漏洩・誤用のリスクが上がる）
- ツール設計例:
  - `get_metric(name, period)` — 指定した指標名の集計値を期間指定で返す
  - `run_funnel(steps, period)` — ファネルの各ステップのコンバージョン率を返す
  - `get_event_count(event, filters)` — イベント発生回数を条件（集計可能な粒度のフィルタ）付きで返す
- 認可・レート制限・監査ログは通常の read-only API と同水準で設計する

### パターン 3: 既製 analytics MCP の接続

- 自前構築の前に、公開されている analytics 系 MCP サーバー（GA4 系等）で代替できないか確認する
- 既製 MCP を使う場合も、渡す権限は read-only スコープに限定する
- プロジェクトに既に接続されている MCP ツール一覧を確認し、analytics/metrics/verification 系の名前があれば優先的に活用を検討する（特定のツール名やベンダーをここで決め打ちしない）

### どのパターンを選ぶか

- 既存の API 基盤がしっかりしている → パターン 1
- DWH/DB への直接クエリが必要で、社内 API 化のコストが高い → パターン 2
- すでに GA4 等の外部 analytics を使っており、公開 MCP で足りる → パターン 3
- 単発の検証で今後繰り返さない → どのパターンも過剰投資になりうる。Level 1/2（既存データ・手動集計）で十分か再検討する

## 計測実装 PR チェックリスト

計測を追加する PR のレビュー・セルフチェックに使う。

- [ ] イベント名が命名規約（`<対象>_<動作>` の過去形スネークケース）に沿っている
- [ ] 既存のイベント体系と重複・矛盾していない（似た意味のイベントを増やしていない）
- [ ] プロパティに不要な PII が含まれていない
- [ ] このイベントが「どの仮説の、どの成功基準の判定に使われるか」がコメントまたは PR 説明に書かれている
- [ ] 発火条件が意図通りか（二重発火、発火漏れがないか）を確認済み
- [ ] 集計・ダッシュボード側で実際に値が拾えることを検証済み（実装しただけで終わっていない）
- [ ] AI エージェント経由でアクセスする想定がある場合、read-only 経路（本ドキュメントのパターン 1〜3）に集計済みの形で乗るか確認した
