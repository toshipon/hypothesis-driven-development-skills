# Verification Methods — 検証手法カタログ

`/hdd:grill`・`/hdd:verify` から参照される、検証手法選定の知識ベース。**作る前に検証し、作るなら計測する** が基本原則。

## 原則

1. **不確実性が高いものから検証する**: 課題仮説が未検証なら、解決策の作り込みより先に課題の実在を確認する
2. **つくらずに学ぶ**: コストの低い検証（インタビュー・データ分析・ファイクドア）で答えが出るなら、プロトタイプや本実装に進まない
3. **学びを資産にする**: どの手法を選んでも、成功基準・撤退基準・観測事実を事前に言語化し、結果を再利用可能な形で記録する

## 手法カタログ

### 1. 顧客インタビュー

- **概要**: 対象ユーザーに直接話を聞き、課題の実在・深刻度・現状の回避行動を確認する
- **検証できる仮説タイプ**: 課題仮説（主）、解決仮説の初期反応（副）
- **コスト**: 低（人件費・調整コストのみ）
- **期間**: 3 日〜2 週間（対象者の確保次第）
- **確信の種類**: 定性
- **実施手順の要点**:
  1. 対象ペルソナに合致する 5〜8 人を確保する
  2. **The Mom Test** の原則で質問設計する: 未来の意図ではなく **過去の具体的な行動** を聞く（「使いますか？」ではなく「直近でその課題にどう対処しましたか」）
  3. 誘導質問を避ける。自分のアイデアを説明してから感想を聞かない
  4. 「良いアイデアですね」等の社交辞令は事実として記録しない
- **落とし穴**:
  - 誘導質問により「欲しい」と言わせてしまう（社交辞令バイアス）
  - サンプルが自社に好意的なユーザーに偏る
  - 発言を事実として記録し、行動の裏付けを取らない

### 2. 既存データ分析

- **概要**: すでに存在するログ・DB・問い合わせ履歴・利用データから仮説を検証する
- **検証できる仮説タイプ**: 課題仮説、価値仮説
- **コスト**: 最安（新規実装・調査コストなし）
- **期間**: 1 日〜数日
- **確信の種類**: 定量
- **実施手順の要点**:
  1. 検証したい指標に対応する既存データソースを特定する（`/hdd:data-infra` の Level 1 相当）
  2. クエリ・集計を行い、傾向を確認する
  3. 相関と因果を混同しない。傾向が見えても「なぜ」は別途検証が必要な場合がある
- **落とし穴**:
  - 見たい結論に合わせて集計条件を後から調整する（p-hacking 的な振る舞い）
  - サンプル期間・母集団の偏りを確認しないまま結論を出す

### 3. ファイクドア / スモークテスト

- **概要**: 実装していない機能へのボタン・ページ・広告を用意し、クリック率や登録率で需要を確認する
- **検証できる仮説タイプ**: 解決仮説、価値仮説
- **コスト**: 低〜中
- **期間**: 1〜2 週間
- **確信の種類**: 定量
- **実施手順の要点**:
  1. 「クリックしたら何が起きるか」を決める（多くは「近日公開です、興味があればメール登録」）
  2. 成功基準（クリック率・登録率）を事前に決める
  3. **倫理面の注意**: ユーザーを欺く形にしない。クリック後は必ず正直な説明（開発中であること）を提示する。既存の有償導線やサポート窓口を偽の機能で塞がない。長期間放置しない
- **落とし穴**:
  - ユーザーの信頼を損なう見せ方（実在しない機能をあるかのように誤認させたまま放置）
  - クリックはしたが本気の需要ではない（好奇心クリック）を区別できない設計にする

### 4. ランディングページ + 広告

- **概要**: 提案する価値を訴求する LP を作り、広告や既存チャネルへの露出で反応を計測する
- **検証できる仮説タイプ**: 課題仮説、価値仮説
- **コスト**: 中（LP 制作 + 広告費）
- **期間**: 1〜3 週間
- **確信の種類**: 定量（一部定性: フォーム自由記述など）
- **実施手順の要点**:
  1. 訴求は 1 つに絞る（複数訴求を同時にテストしない）
  2. CTA（登録・問い合わせ）のコンバージョン率を成功基準にする
  3. 広告出稿する場合は流入セグメントを対象ペルソナに絞る
- **落とし穴**:
  - LP のデザイン・コピーの質が結果を左右し、仮説そのものの検証と混同しやすい
  - 広告ターゲティングが対象ペルソナとずれている

### 5. プロトタイプ / ユーザビリティテスト

- **概要**: モックやプロトタイプを実際に操作してもらい、使えるか・意図通り使われるかを観察する
- **検証できる仮説タイプ**: 解決仮説
- **コスト**: 中
- **期間**: 1〜2 週間
- **確信の種類**: 定性
- **実施手順の要点**:
  1. タスクベースで観察する（「これを使って◯◯してください」）。感想を聞く前に行動を観察する
  2. 5 人前後のテストで大半のユーザビリティ課題は発見できる
  3. 発話思考法（think aloud）で迷いのポイントを可視化する
- **落とし穴**:
  - 操作を誘導してしまい、本来の迷いを見逃す
  - 「使えた」と「価値を感じた」を混同する（ユーザビリティは解決仮説の検証であり、価値仮説の検証ではない）

### 6. コンシェルジュ / オズの魔法使い

- **概要**: 自動化・システム化する前に、裏側を手動オペレーションで代替してユーザーに提供する
- **検証できる仮説タイプ**: 解決仮説、価値仮説
- **コスト**: 中（人的オペレーションコスト）
- **期間**: 2〜4 週間
- **確信の種類**: 定性 + 定量（継続利用率等）
- **実施手順の要点**:
  1. コンシェルジュ（ユーザーに手動対応と伝える）とオズの魔法使い（裏側が手動と伝えない）のどちらにするか決める。後者は倫理的な配慮が必要
  2. 少人数の対象者に、実際の価値提供を手動で行う
  3. 継続利用意向・満足度・実際の行動変化を計測する
- **落とし穴**:
  - スケールしないオペレーションで得た結果を、自動化後の結果と同一視してしまう
  - オズの魔法使い形式でユーザーを欺いたまま終了し、事後説明をしない

### 7. A/B テスト

- **概要**: 既存プロダクト上でユーザーを群に分け、変更の有無による指標差を統計的に検証する
- **検証できる仮説タイプ**: 価値仮説
- **コスト**: 中〜高（実装 + 十分なトラフィックが前提）
- **期間**: 効果量とトラフィックに依存（最低でも 1〜2 週間、季節性がある指標はさらに長く）
- **確信の種類**: 定量
- **実施手順の要点**:
  1. 検出したい効果量（例: CVR 5% → 6%）を事前に決める
  2. **サンプルサイズの目安**: ベースライン CVR・検出したい最小効果量・有意水準（通常 5%）・検出力（通常 80%）から算出する。目安として、ベースライン CVR が低い（〜数%）ほど必要サンプル数は急増する。厳密な算出はサンプルサイズ計算ツール/ライブラリを使う
  3. 十分なトラフィックがない場合は A/B テストを選ばず、他の手法（コンシェルジュ、段階的ロールアウト）を検討する
  4. 有意水準に達する前に停止しない（p-hacking の回避）
- **落とし穴**:
  - トラフィック不足のまま実施し、有意差が出ないことを「効果なし」と誤判定する
  - 複数指標を同時に見て、都合の良い指標だけを成功と主張する（多重検定問題）

### 8. 段階的ロールアウト + 計測

- **概要**: 新機能を一部ユーザー・地域・セグメントに限定リリースし、計測しながら拡大判断する
- **検証できる仮説タイプ**: 価値仮説
- **コスト**: 中
- **期間**: 継続的（拡大判断のたびに評価）
- **確信の種類**: 定量
- **実施手順の要点**:
  1. 最初の展開範囲を決める（社内 → 一部顧客 → 全体、等）
  2. 各段階の拡大基準（数値）を事前に決める
  3. フィーチャーフラグ等で即座にロールバックできる状態を維持する
- **落とし穴**:
  - 拡大基準を決めずに感覚で拡大してしまう
  - 初期セグメントが全体を代表していない（アーリーアダプター偏重）

### 9. プレセールス / LOI（Letter of Intent）

- **概要**: BtoB 向けに、実装前に契約意向書・発注確約・前払いなどの具体的なコミットメントを取り付ける
- **検証できる仮説タイプ**: 価値仮説（BtoB）
- **コスト**: 低（金銭的投資はほぼゼロ、営業工数のみ）
- **期間**: 商談サイクルに依存（2 週間〜数ヶ月）
- **確信の種類**: 定量（成約数・金額）+ 定性（商談での反応）
- **実施手順の要点**:
  1. 実際の商談で、実装前提の提案として価格・納期を提示する
  2. 「興味がある」ではなく LOI・発注書・前払いなど **具体的なコミットメント** を求める
  3. 断られた理由を必ず記録する（価格・機能・タイミング等）
- **落とし穴**:
  - 「口約束」を成約と同一視する（本当のコミットメントかどうかを見極める）
  - 大口 1 社の反応で全体を判断する

## 選定マトリクス

仮説タイプ × 確度 × コストの目安。「◎」が第一候補、「○」が次点。

| 手法 | 課題仮説 | 解決仮説 | 価値仮説 | コスト |
|------|:---:|:---:|:---:|------|
| 顧客インタビュー | ◎ | ○ | - | 低 |
| 既存データ分析 | ◎ | - | ○ | 最安 |
| ファイクドア/スモークテスト | - | ○ | ◎ | 低〜中 |
| LP + 広告 | ○ | - | ◎ | 中 |
| プロトタイプ/ユーザビリティ | - | ◎ | - | 中 |
| コンシェルジュ/オズの魔法使い | - | ◎ | ○ | 中 |
| A/B テスト | - | - | ◎ | 中〜高 |
| 段階的ロールアウト | - | - | ◎ | 中 |
| プレセールス/LOI | - | - | ◎（BtoB） | 低 |

**選び方の指針**:

1. まず課題仮説が未検証なら、インタビュー or 既存データ分析を最優先する（他の手法より安く、他の全ての土台になる）
2. 解決仮説の検証には、実装コストの低い順に「プロトタイプ提示 → コンシェルジュ → 実装」を検討する
3. 価値仮説（数値インパクト）の検証は、トラフィックがあれば A/B テスト、なければファイクドアや段階的ロールアウトを使う
4. 複数手法を組み合わせてよい（例: インタビューで課題確認 → ファイクドアで需要の量を確認）

## 成功基準設計の原則

1. **先行指標を使う**: 遅行指標（売上・解約率等）だけでなく、より早く観測できる先行指標（登録率・初回利用率等）を成功基準にする
2. **基準は事前にコミットする**: 結果を見てから基準を後付けしない。検証開始前に数値と期限を確定させる
3. **撤退基準は必須**: 「成功基準を満たさなかったら何をするか（pivot/kill）」まで決めていない検証は、検証として不完全
4. **判定できる粒度にする**: 「反応が良ければ」のような定性的すぎる基準は避け、「◯% 以上」「◯件以上」等、後から機械的に照合できる形にする
