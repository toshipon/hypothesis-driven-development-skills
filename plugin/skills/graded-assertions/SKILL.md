# Graded Assertions — 断定しない出力

可否判定・リスク評価・診断を「できます / できません」と言い切る設計は、外れた瞬間に信頼（Trust）を毀損する。逆に、根拠の確度を明示して「ここから先はあなたが確認する」と線を引く出力は、外れても信頼が残る。**断定しないことは弱さではなく製品要件**。

## 三分割の定義

| ラベル | 条件 | 書き方の例 |
|---|---|---|
| **確定** | 一次情報（原文・公式発表・実測）で直接確認済み | 「新宿区は条例で月〜金の営業を制限しています（区条例第 X 条、原文確認済 [S3]）」 |
| **推定** | 二次情報・類推・モデル出力が根拠。一次確認が未了 | 「周辺事例から ADR は 18,000〜22,000 円と推定されます（裏付け: M4、一次統計未確認）」 |
| **未確認** | 根拠がない、または確認手段が未実行 | 「消防設備の適合状況は未確認です。管轄消防署への事前相談で確定します」 |

判定の見出しやサマリーに、どのラベルかを**視覚的に**付ける（例: ✅ 確定 / 🔶 推定 / ❓ 未確認）。

## 出力に必ず含める 3 点セット

1. **三分割された結論** — 全体を 1 つの結論に丸めない。項目ごとにラベルを付ける
2. **要確認リスト** — 未確認・推定を確定に変えるための具体的アクション（誰に・何を・どうやって確認するか）
3. **免責** — この判定が保証でないこと、最終確認は権限ある窓口（行政・専門家・当事者）で行うべきことを 1〜2 行で明記

```markdown
## 要確認リスト

- [ ] <項目>: <確認先> に <確認方法> で確認（推定 → 確定に上がる条件: ...）

> **免責**: 本判定は YYYY-MM-DD 時点の公開情報に基づく参考情報であり、可否を保証するものではありません。最終判断の前に <確認先> にご確認ください。
```

## 機能設計への適用（判定を返すプロダクトの場合)

- 出力スキーマにラベル（confirmed / estimated / unverified）を必ず持たせる。UI で 3 値を出し分けられない設計にしない
- 各判定に根拠 ID（出典・条文・データ行）を紐付け、後から辿れるようにする（→ `source-traceability` skill）
- 「未確認」を減らすアクション（行政照会・実測・書類取得）を、そのままユーザーの次のタスクとして提示する。ここが分析ツールと System of Action の分岐点
- 予測値（推定）には後で実績と突き合わせる ID を付ける。予測 vs 実績が Outcome Data になる

## アンチパターン

- 全項目を「問題ありません」に丸めたサマリー
- 免責だけ長くて要確認リストがない出力（責任回避であって支援ではない）
- 推定を確定のトーンで書き、脚注にだけ「※要確認」と書く
- LLM の出力をそのまま「確定」として通す（LLM 出力は常に推定から始まる）
