# Moat Test — AI 時代の競争優位の判定

## 前提

AI によりソフトウェアを作るコストは急落する。したがって **Code × UI × LLM Prompt は Moat ではない**。Moat は以下の 7 つに置く。

| 源泉 | 意味 | 例 |
|---|---|---|
| Distribution | ユーザーに届く経路を持っているか | 仲介会社の紹介枠、自治体説明会、SEO |
| Workflow Ownership | ユーザーの業務フローの中に居座っているか | 苦情対応記録が毎日ここで行われる |
| Proprietary Data | 他社が取れないデータを蓄積しているか | 行政回答、融資否決理由、成約価格 |
| Outcome Data | 予測 vs 実績を取れているか | 予測 ADR vs 実 ADR、可否判定 vs 許可結果 |
| Domain Knowledge | 構造化に人手と時間がかかる知識か | 条例の 11 の構造的難所 |
| Trust | 責任を引き受けているか | 出典トレーサビリティ、ハッシュチェーン証跡 |
| Network Effects | 参加者が増えるほど価値が上がるか | 投資家 × 仲介 × 金融機関 |

## 手順

### Step 1: Claude Test

> 「Claude Code を持った優秀なエンジニアが 3 か月でコピーできるか？」

- **YES** → その機能自体は Moat ではない。次を問う: **「コピーした競合が取得できないデータ・関係・ワークフローは何か？」** それが答えられないなら機能単体は KILL 候補
- **NO** → なぜ 3 か月で無理なのかを言語化する（大抵は「データの継続収集」「人手レビュー」「関係構築」「規制知識」のどれか）。それが Moat の源泉

### Step 2: Foundation Model Test

> 「GPT / Claude の能力が今の 10 倍になった場合、この機能・会社の価値は下がるか？」

- **下がる** → LLM の能力そのものを売っている。KILL または再設計（例: 「AI 条例チャット単体」）
- **上がる** → 理想。LLM 性能 ↑ → 自動化率 ↑ → 人的コスト ↓ → 扱える件数 ↑ → Transaction / Data ↑ → 精度 ↑ のループになっているか確認する
- **変わらない** → LLM 非依存の価値（データ・証跡・関係）。悪くないが、LLM をエンジンとして使い切れていない可能性を検討する

### Step 3: Moat 源泉マップ

7 源泉それぞれについて「この機能はこれを **獲得する** か / **消費する** か / **無関係** か」を書く。獲得が 0 個の機能は、ユーザー獲得目的（Distribution）でない限り優先度を下げる。

### Step 4: Outcome Data 設計

- この機能が出す **予測・判定** は何か
- それに対応する **実績** はいつ・どこから取れるか（取れないなら「取れる形に直せるか」）
- 予測と実績を紐付ける ID は設計に含まれているか

### Step 5: System of Action での位置

ユーザーのワークフロー全体（例: 探す → 判断する → 買う → 開業する → 運営する → 改善する）を書き、この機能がどの段階か、前後の段階へ **手を伸ばせるか** を書く。分析だけで終わる機能（URL → 分析 → コメント）は Workflow Ownership を獲得しない。

### Step 6: 断定しない出力か

判定・推定を返す機能なら、出力が「確定 / 推定 / 未確認」に分かれ、要確認リストと免責を伴うかを確認する。断定する設計は Trust を毀損する。

## 出力テンプレート（Go / Kill ボードに貼れる形）

```
### <機能・アイデア名>

- Claude Test: YES / NO — <理由 1 行>
- 競合が取れないもの: <データ / 関係 / ワークフロー>
- Foundation Model Test: 下がる / 変わらない / 上がる — <理由 1 行>
- Moat 源泉: 獲得 [..] / 消費 [..]
- Outcome Data: 予測 <X> ↔ 実績 <Y>（取得元: <Z>）
- System of Action 位置: <段階>（前後: <伸ばせる段階>）
- 断定しない出力: ✓ / ✗
- 判定: 🔴 KILL / 🟡 要検証 / 🟢 GO 候補 / 🔵 構想 — 復活条件 or 次アクション
```

## 適用例（民泊規制コンプライアンス SaaS の構想を評価した例）

| 機能 | Claude Test | FM Test | 獲得する源泉 | 判定 |
|---|---|---|---|---|
| AI 条例チャット単体 | YES | 下がる | なし | 🔴 KILL |
| URL → 英語で投資分析 | YES | 下がる | なし | 🔴 KILL |
| Rule Engine（条例の継続収集 + 人手レビュー + 版管理） | NO（データ収集と一次確認が律速） | 上がる（抽出コスト ↓） | Domain Knowledge, Proprietary Data, Trust | 🟢 GO 候補 |
| Complaint Log（苦情対応の証跡） | YES（機能は単純） | 変わらない | Workflow Ownership, Trust, Outcome Data | 🟢🟢 本命の一部（機能でなくワークフローに価値） |
| 行政問い合わせ Agent | YES（生成は容易） | 上がる | **行政回答の蓄積**（Proprietary Data） | 🔵 構想 — 回答をデータとして保存する設計が条件 |

## 注意

- このテストは「作らない理由」を探すためではなく **「どこに投資するか」を決める** ためのもの。Claude Test に落ちても、Distribution やワークフロー入口として必要な機能はある（ただし Moat と呼ばない）
- 判定は Go / Kill ボード（例: `docs/go-kill-board.md`）の判定履歴に絶対日付付きで残す。過去の KILL を黙って覆さず、復活させるなら復活条件と根拠を書く
- `/hdd:grill` で仮説カードを作った後、その解決仮説に対してこのテストを通し、結果を仮説カードの判定根拠に含めるのが基本の流れ
