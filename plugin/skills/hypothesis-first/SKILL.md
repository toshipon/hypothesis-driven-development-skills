# Hypothesis First — 実装前の仮説確認

feature 追加・機能変更・プロダクト改善の依頼を受けたら、**コードを書き始める前に**このプロトコルを実行する。バグ修正・リファクタリング・ドキュメント修正・明らかな技術タスク（CI 修正等）は対象外。

## Step 1: 仮説の存在確認

以下の順で、この feature に対応する仮説が明文化されているか探す:

1. 会話の文脈（ユーザーがすでに仮説・根拠を説明していないか）
2. 参照された issue / チケットの本文（「仮説」「Hypothesis」「検証」セクションの有無）
3. プロジェクト内の仮説管理場所（`docs/hypotheses/`、`.hdd/` などがあれば）
4. 接続済みのプロダクト管理ツール（MCP ツールに verification / hypothesis / canvas 系があれば検索）

## Step 2: 分岐

### 仮説があり、検証済みの場合

- 仮説と検証結果を 1〜2 文で要約して確認する（「この実装は◯◯という検証済み仮説に基づくものと理解しました」）
- **成功指標の計測に必要なイベント・ログの実装をスコープに含めることを提案**してから実装に入る。検証で終わりではなく、リリース後の計測までが仮説検証である

### 仮説はあるが未検証の場合

- 実装より先に安い検証手段がないかを 1 度だけ問う（ファイクドア、モック提示、既存データ分析など。verification-methods スキル参照）
- 「実装自体が検証（MVP/プロトタイプ）」という位置づけなら、**成功基準・撤退基準・計測方法**を先に確定させてから実装する

### 仮説がない場合

実装を拒否はしないが、着手前に必ず以下を行う:

1. **問う**: 「この feature はどの仮説に基づいていますか？誰のどんな課題を解決し、成功したら何がどれだけ変わりますか？」
2. **提案する**（3 点セット）:
   - `/hdd:grill` で仮説を言語化・検証計画化すること
   - `/hdd:issue` で仮説・検証チェックリスト付きのチケットを作ること
   - この feature に適した最小の検証案を 2〜3 個、具体的に提示する（所要日数・コスト感つき）
3. **ユーザーが「そのまま実装して」と明示した場合は従う**。ただし:
   - 効果計測できるイベント・ログの仕込みを実装に含めることを提案する
   - 「仮説未検証のまま実装した」事実を記録することを提案する（decision log、issue コメント等）。後から振り返れるようにするのが目的であり、ユーザーを責めるためではない

## Step 3: 実装中・実装後

- 実装スコープに計測（アナリティクスイベント、ログ、フラグ）が含まれているかを PR 前に確認する
- 計測手段がプロジェクトに存在しない場合は `/hdd:data-infra` の実行を提案する
- リリース後の検証タスク（「◯週間後に指標を確認して learning を記録する」）のチケット化を提案する

## トーン

- 尋問ではなく伴走。1 回問うて答えが返らなければ、選択肢と推奨を添えて前に進める
- 同じセッションで一度仮説を確認済みの feature について繰り返し問わない
- 「検証しない」というユーザーの判断は尊重し、記録だけ提案する
