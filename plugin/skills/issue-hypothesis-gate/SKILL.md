# Issue Hypothesis Gate — チケット作成前の仮説ゲート

このプラグインには 2 段構えのゲートがある。hooks（PreToolUse）はチケット作成コマンド・ツール呼び出しをマーカー文字列の有無だけで機械的に検査する**強制の最終ライン**であり、仮説セクションが無ければ有無を言わさず exit 2 でブロックする。この skillはそれより手前で発動する**事前の丁寧なゲート**で、作成しようとしている本文を実際に読み、内容が体裁だけでなく実質を伴っているかを確認し、欠落があれば作成前にユーザーと一緒に埋める。skill を通しておけば hooks は素通りになるはずだが、skill を経由せず直接ツールを叩いた場合でも hooks が最終防衛する。

## 適用対象

`gh issue create` / `glab issue create` / `jira issue create` などの CLI 実行、および issue・backlog・ticket・story・task を作成する MCP ツール（`create_issue` / `create_backlog_item` / `create_ticket` / `create_story` / `createIssue` / `create_task` 等、ツール名は接続先によって異なる）の呼び出し。これらを実行する**直前**に必ず適用する。

## Step 1: チケット種別を判定する

- バグ修正 → Step 2-A
- 技術基盤タスク（CI 整備、リファクタリング、依存更新、計測基盤整備など） → Step 2-B
- それ以外（feature 追加、UI 変更、新機能、プロダクト改善など） → Step 2-C

## Step 2-A: バグ修正

仮説セクションは不要。ただし「直す価値」（誰がどう困っていて、放置するとどうなるか）を一言だけ確認する。答えがあれば、または自明であればそのまま進める。

## Step 2-B: 技術基盤タスク

仮説カードは不要だが、「これで何ができるようになるか」という効果を本文に一行以上含めることを求める。含まれていなければ追記案を提示する。

## Step 2-C: feature・改善タスク

以下のチェックリストで本文を検査する。

- [ ] 誰のどんな課題かが明文化されている
- [ ] 課題の根拠（観測された事実）が書かれている
- [ ] 成功指標と目標値がある
- [ ] 検証方法と成功基準・撤退基準がある
- [ ] 「このタスクをやらない場合に失うもの」が書かれている

欠落があれば、作成前にユーザーに指摘し、既存の情報から埋められる範囲で具体的な追記案（穴埋めできる文面）を提示する。`/hdd:grill` や `/hdd:issue` の使用も選択肢として案内する。

## Step 3: ユーザーが仮説不要と明示した場合

指摘してもユーザーが「そのまま作成して」など仮説セクション不要の意思を明示した場合は、本文に `[no-hypothesis]` マーカーを 1 行含めて作成する。これは hooks の機械チェックを正しく通過させるためでもある。

## トーン

- 尋問ではなく伴走。追記案は具体的な穴埋め文面として提示し、ユーザーの入力負担を最小化する
- 同じセッションで既にこのゲートを通過した本文について繰り返し確認しない
- hooks に一度ブロックされてこの skillが呼ばれた場合は、そのブロックメッセージを踏まえて素早く追記案を出す
- 「検証しない」というユーザーの判断は尊重し、`[no-hypothesis]` マーカーの付与だけを提案する
